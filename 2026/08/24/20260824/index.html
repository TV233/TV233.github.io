# 问题现象

在 iPad 端和 iPhone 端使用哔哩哔哩 App 播放高画质视频时，出现了一个很有规律的异常：

  • 播放 4K 时，下载速度长期维持在约 118 KB/s，视频频繁缓冲；
  • 切换到 1080P60 后，有时会立刻恢复正常速度；
  • 但在另一次测试中，1080P60 也出现了相同的限速；
  • 设备通过某代理软件联网，并启用了哔哩哔哩去广告插件。

最初看起来很像 “B 站对 4K 单独限速”，也可能怀疑是代理线路、软件分流或去广告插件造成的。通过四轮抓包，最终发现真正的问题是：

哔哩哔哩将视频主地址调度到了部分性能异常的 MCDN 节点。这些节点或其跨运营商路径只能提供约 1 Mbit/s 的有效带宽，但连接仍持续正常返回数据，播放器因此没有及时切换到高速备用源。

最终通过代理软件的重写功能在请求阶段统一阻断 os=mcdn ，迫使播放器立即使用服务端已经下发并签名的备用 CDN 地址，问题得到解决。

# 一、118 KB/s 为什么值得注意

抓包中多个完整 Range 请求的下载速度都非常接近：

下载大小耗时有效速度
1,048,576 B9.38 秒约 109 KiB/s
601,439 B4.99 秒约 118 KiB/s
447,137 B3.77 秒约 116 KiB/s
424,869 B3.54 秒约 117 KiB/s

118 KB/s × 8 大约是 0.94 Mbit/s 。考虑 TCP/IP 开销后，这很像一个接近 1 Mbit/s 的固定整形或节点上行带宽上限，而不像普通网络拥塞造成的随机波动。

对于平均码率约 2.8～3.7 Mbit/s 的 4K/HDR 视频，这个速度显然无法持续播放。即使是约 1.64 Mbit/s 的 1080P60，也会在缓冲耗尽后卡顿。

# 二、第一轮抓包：切换画质后恢复，不代表 4K 被账户限速

第一轮抓包中，高画质视频最初从一个速度异常的节点下载，速度稳定在约 118 KB/s。切换至 1080P60 后，播放器建立了新的媒体连接，并落到了另一个高速节点，网速随即恢复。

稍后再次请求相同的 4K 流时，它又能从另一个节点高速下载。

这已经说明：

  1. 限速不是持续绑定在账号或 4K 画质上的；
  2. 同一个视频表示换一个节点就能恢复；
  3. 切换画质的真正作用，很可能是触发重新获取播放地址和重新选源。

因此，“1080P60 恢复正常” 只是重新调度成功的表象，而不是 1080P60 解除了某种画质限速。

# 三、第二轮抓包：同一条 4K 流自动换节点后恢复

第二轮抓包捕捉到了更完整的故障转移过程。

# 故障节点

两个 Range 请求都没有顺利完整交付。约 4.3 秒后，播放器对尚未完成的同一区间发起了重叠请求，但目标变成：

切换前后的请求具有以下共同点：

  • 相同的视频文件；
  • 相同的视频流编号 30121 ；
  • 相同的文件总长度；
  • 相同的 bw 参数；
  • Range 区间相互重叠并衔接。

也就是说，播放器没有降低画质，而是对同一条 4K 流执行了主备地址切换。

切换到 os=estgoss 后，连续 1 MiB 请求通常只需约 90～115 ms，瞬时速度可达约 9～11 MiB/s。问题的分界点非常明确：

IP 归属也提供了旁证：慢节点位于四川联通地址段，而恢复后的节点位于中国移动地址段。在移动网络访问联通 MCDN 的场景下，节点自身性能或跨运营商路径都可能成为瓶颈。APNIC：124.161.0.0/16

# 四、全局直连测试：排除代理和分流策略

为了排除代理节点及分流规则的影响，第三轮测试将代理模式切换为全局直连。

问题仍然出现。

本次实际取得的是 qn=125「真彩 HDR」 视频表示，服务端元数据为 1920×1080、30fps ，并不是通常的 qn=120 4K 。但它复现了完全相同的固定限速：

一个完整的 1 MiB Range 请求耗时约 9.38 秒，有效速度约 109 KiB/s。该地址位于四川联通 112.192.0.0/14 地址段。APNIC：112.194.0.0

因为这次是全局直连，可以排除：

  • 代理服务器带宽不足；
  • 代理软件将两个媒体 IP 分配到不同代理策略；
  • 境外代理绕路。

问题边界因此缩小为：

B 站调度的 MCDN 节点本身，或者客户端运营商到该节点的直连路径。

# 为什么没有自动切换备用源

这次的慢节点虽然速度严重不足，却始终以约 1 Mbit/s 持续传输，并正常返回 HTTP 206 Partial Content ：

  • 没有 429 ；
  • 没有 Retry-After ；
  • 没有明显连接中断；
  • Range 最终仍能完成。

这可能导致播放器把连接判断为 “仍然健康”。它通常更容易在连接失败、Range 长时间完全不动或超时后切换备用源，而不是因为吞吐量低就立即切换。因此会出现 “始终很慢，但一直不换节点” 的现象。

# 五、去广告插件是否修改了视频地址

全局直连只改变出站策略，并不会关闭代理软件的 MITM 和脚本处理。抓包显示，去广告插件确实拦截并重新编码了：

这个接口非常关键，因为其中包含播放器使用的主地址和备用地址。

为排除插件影响，我对改写前后的 gRPC protobuf 做了逐字段比较：

  • 改写前后均包含 256 个叶字段值；
  • 删除字段为 0；
  • 新增字段为 0；
  • 24 条媒体 URL 的内容和先后顺序完全一致；
  • 所有 .m4s 媒体响应都没有被插件修改。

正文体积从约 3.2 KiB 增大到约 16 KiB，是因为插件把 gzip 压缩的 gRPC 消息解压并重新编码，而不是删除或替换了 CDN 地址。

因此，本次使用的去广告插件不是限速的直接原因。

同一次测试中，1080P60 使用了另一条视频流：

它同样被限制在约 109～118 KiB/s。由于原正则只匹配 3012x ， 30106 没有被阻断，所以播放器一直留在慢 MCDN 节点。

这进一步确认：

问题并非 4K 专属。只要高码率视频被分配到这种约 1 Mbit/s 的 MCDN 节点，1080P60 也会卡顿。

# 八、为什么不能把 MCDN URL 直接改成另一个域名

每一个主地址和备用地址都具有独立的签名参数，例如：

不同来源的 upsig 并不相同。直接把慢地址的 IP、域名或 os=mcdn 改成 os=estgoss ，很可能破坏签名并得到 403 。

因此，本方案并不伪造或修改媒体 URL，只让播放器从 B 站已经下发的合法备用地址中自行选择。

# 九、风险与更保守的替代规则

直接阻断所有 os=mcdn 也会影响音频，因为部分 30216/30232/30280 音频流同样可能使用 MCDN。我的测试中音视频都能正常回退，但不能保证每个视频、地区和 App 版本都一定提供可用备用地址。

如果出现无声、启动变慢或直接播放失败，应立即停用规则。

  • 300xx/301xx 通常是视频；
  • 302xx 通常是音频。

另一种更理想、但实现更复杂的方案，是直接修改 PlayURL/PlayView 的 protobuf：当 base_url 为 MCDN 时，将现有 backup_url 中第一个非 MCDN 地址提升为主地址。这样不会先产生一次失败请求，但需要维护适配 App protobuf 结构的脚本。

# 十、配置语法常见问题

配置时曾遇到一次语法错误，原因是从富文本复制后，ASCII 符号被替换成全角字符，或者正则被自动换行。

需要特别确认：

  • 使用半角 { } ? : | ；
  • 整条规则保持在同一行；
  • 不要把 Markdown 代码围栏一起复制；
  • 如果编辑完整配置，只保留一个 [Rewrite] 段；
  • 修改后完全结束哔哩哔哩 App，避免继续使用旧连接和已缓存的 PlayURL。

# 十一、最终结论

整个问题可以归纳为：

  1. B 站 App 的 PlayURL 同时下发主地址和多个备用地址；
  2. 主地址有时是带 os=mcdn 的 IP 直连节点；
  3. 部分 MCDN 节点或跨运营商路径存在接近 1 Mbit/s 的固定速度上限；
  4. 节点仍持续返回 HTTP 206 ，播放器不会及时认为它已经失效；
  5. 切换画质之所以偶尔恢复，是因为触发了重新获取地址和重新选源；
  6. 全局直连下仍能复现，排除了代理线路和普通分流策略；
  7. 去广告插件虽然重新编码了 PlayURL protobuf，但没有修改媒体 URL；
  8. 根据稳定特征 os=mcdn 阻断请求后，播放器会立即使用高速备用源。

最终有效规则：

这次排查也说明，面对 “切换画质后网速突然恢复” 这种现象，不能只比较画质码率，更应该比较切换前后的 CDN 地址、URL 参数、Range 下载节奏和播放器的主备源行为。
